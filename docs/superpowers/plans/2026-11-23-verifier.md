# Verifier Implementation Plan

> **For agentic workers:** Work through this plan task by task, in order. If you have the superpowers skills, use superpowers:subagent-driven-development or superpowers:executing-plans. Steps use checkbox (`- [ ]`) syntax for tracking. Tasks 1 and 7 end with a **stop**: report to the course owner and wait for their answer before continuing.

**Goal:** Build the checks that catch a confidently wrong analysis: an analyst's answer that looks finished and is not right because of duplicate rows, a join that repeats rows, a unit that changes part-way through a series, or a number that its own SQL does not produce. Then measure how many wrong answers the checks catch and how often they raise a false alarm.

**Architecture:** The verifier is code, not a prompt. After an analyst finishes, it takes the analyst's reported SQL, number and datasets, and runs a fixed set of checks against the same database through the same read-only connection. Two of the checks are differential: they re-run the analyst's own query with one table replaced by a corrected version of itself (duplicates removed, or one row per join key) and see whether the number moves. Findings go back to the orchestrator with the analyst's answer, and into the record of the run. A small set of trap tables with known right and wrong answers tests every check without a model.

**Tech Stack:** Python 3.11 or later; SQLAlchemy 2.0; standard library. `pytest`. Nothing new to install.

**Spec:** There is no separate spec. The next section is the spec. This plan follows `2026-11-23-dataset-catalogue-and-recommendation-test.md` (the "catalogue plan") and `2026-11-23-mcp-servers-and-orchestrator.md` (the "orchestrator plan") and uses what they built.

## Background and decisions

**Why this exists.** The course owner is building an advanced challenge for data scientists on a course about agentic development. Of all its parts, the owner's source material calls this one probably the most valuable: an agent produces a clean report with a wrong number, and the student builds the verification that catches it. This plan builds the instructor's reference verifier and measures it. The orchestrator plan deliberately left it out, but made analysts report their SQL, their datasets and their caveats so that it could be added without changing them.

**This plan was drafted before either earlier plan had been run.** Its author had no access to the system or the data. Thresholds are first guesses. Task 1 checks what the orchestrator plan's report says actually went wrong; if the real causes of wrong answers are not the ones the checks below look for, say so to the owner before building.

Assumptions:
- `dataset-challenge/datacat/` and `dataset-challenge/datachallenge/` exist and their tests pass.
- A results directory from the orchestrator plan exists whose `runs.jsonl` lines carry `analysts` (each analyst's datasets, task, final and stop reason).
- Analysts write SQL with tables as `schema.table`, as the data server's tool description tells them to.

**Decided by the course owner:**

- The traps that matter: duplicate rows, a unit change mid-series, a join that silently multiplies rows.
- Verification is something that can be built and inspected, not a second model being asked whether the first one was right.

**Decided by the plan's author (the owner can overrule any of these):**

- **A check fails an answer only on evidence that the number is affected.** A risk in the data that the query may or may not have handled is a warning. This keeps false alarms low enough for a failure to mean something.
- **Findings annotate; they do not block.** The orchestrator sees the findings and may send the analyst back once, or pass the answer on marked as not verified. The verifier never changes an answer.
- **No SQL parser.** Checks work from what the database reports a query reads, from the catalogue, and from re-running the query with a table shadowed by a common table expression. This is cruder than parsing and has known blind spots, listed under Review Focus. It needs nothing installed.
- **A second, independent analyst is optional and off by default.** It doubles the analysis cost. It is included because it catches what no fixed check anticipates, and so the report can say what it costs against what it catches.
- **Trap tables are synthetic and live only in a test database.** Nothing is planted in real data.
- **Verification applies to orchestrated runs only.** The single-agent baseline does not report its SQL.

## Global Constraints

Everything in the two earlier plans' Global Constraints still applies. In addition:

- **Verification queries are generated by code, never by a model,** apart from the analyst's own statements, which are re-run only through `sqlguard.run_query` with the analyst's scope.
- **Every verification query runs under the statement timeout.** A check that times out or errors produces an `info` finding saying it could not run. It never fails the answer and never stops the run.
- **A cap on work per answer:** at most 30 verification queries per analyst result. Past that, remaining checks report that they were skipped.
- **Trap tables are created only in SQLite or in the scratch PostgreSQL database** named by `DATACAT_TEST_PG_URL`, in their own schema. Never in a database holding real data.
- **Do not tune a threshold until the false alarms on the owner's questions go away.** Report the false alarms. Thresholds change only with the owner's agreement, and the trap tests must still pass.
- **Findings are written in plain language with the numbers that support them,** so a student can check the finding by hand.

## Review Focus

Conditions the tasks' main tests would otherwise miss, and the known blind spots. Each has a test in the task named.

1. **The analyst reports a number its SQL does not produce.** Expect: `fail` from the reproduce check (Task 3).
2. **The data has the problem but the query handled it** (for example it already uses `DISTINCT`). Expect: the differential checks stay quiet, because the number does not move (Task 4).
3. **A verification query times out or the table cannot be compared** (a `json` column defeats `DISTINCT`). Expect: an `info` finding, the other checks still run (Tasks 3 and 4).
4. **The analyst's SQL cannot be shadowed** (it uses `WITH RECURSIVE`, or references the table without its schema inside a quoted mixed-case name). Expect: an `info` finding that the check could not be applied, not a pass (Task 4).
5. **The answer is one row among many** (a grouped result). Expect: the differential checks report that they apply only to single-row results, and the reproduce check still runs (Tasks 3 and 4).
6. **A correct answer.** Expect: verdict `passed`, with no warnings, on the clean trap cases (Tasks 3 to 5).

### Task 3: Findings and the reproduce check

**Files:**
- Create: `datachallenge/verify.py`
- Test: `tests/test_verify.py`

**Interfaces:**
- Consumes: `sqlguard.run_query`, `SqlRejected`, `expand_scope`, `tables_read`; `datacat.entry.Entry`.
- Produces:

```python
@dataclass
class Finding:
    check: str
    severity: str            # "fail", "warn" or "info"
    dataset: str | None      # a dataset id, when the finding is about one
    message: str             # plain language, with the numbers
    evidence: str            # the SQL run and what it returned, at most 1,000 characters

@dataclass
class Located:               # where the reported number sits in the analyst's own results
    statement: int           # index into final["sql"]
    column: int
    sql: str
    single_row: bool

@dataclass
class VerifyContext:
    engine: Engine
    entries: dict[str, Entry]        # the analyst's datasets, by id
    allowed: set[str]                # expand_scope of those datasets
    final: dict                      # the analyst's finish arguments
    max_rows: int = 50
    max_queries: int = 30
    located: Located | None = None
    queries: int = 0

CHECK_ORDER = ("reproduce", "duplicates", "fanout", "series_break", "missing_values", "caveats")

def run_checked(ctx: VerifyContext, sql: str) -> QueryResult      # run_query with ctx's scope; counts the query
def entry_for(ctx: VerifyContext, relation: str) -> Entry | None  # "schema.name" -> the entry, if in scope
def mentions(sql: str, column: str) -> bool                       # whole word, any case
def check_reproduce(ctx: VerifyContext) -> list[Finding]
def register(name: str, check: Callable[[VerifyContext], list[Finding]]) -> None
def verify(ctx: VerifyContext, checks: list[str]) -> list[Finding]
def verdict(findings: list[Finding]) -> str                       # "failed", "warnings" or "passed"
```

- `run_checked` raises `RuntimeError("query limit reached")` once `ctx.queries` equals `max_queries`.
- `check_reproduce`: if `final["value"]` is `None`, return nothing. If `final["sql"]` is empty: `fail`, "A number was reported with no SQL to support it." Run each statement with `run_checked`; a statement that is rejected or errors: `fail`, quoting the message. Look for the reported value among the numeric cells of each result's rows, last statement first, matching when `abs(cell - value) <= max(0.005, 1e-6 * abs(value))`. Found: set `ctx.located` (with `single_row` true when that result has exactly one row) and return nothing. Not found: `fail`, "The reported value {value} does not appear in the results of the reported SQL. The last statement returned {first cell}."
- `verify` runs the named checks in `CHECK_ORDER`, always running `reproduce` first when any other check is named, even if it is not. A check that raises produces one `info` finding, "The {name} check could not run: {message}", and the rest continue. An unknown check name raises `ValueError`.
- `verdict`: `failed` if any finding is `fail`; else `warnings` if any is `warn`; else `passed`.

### Task 4: The differential checks: duplicates and join fan-out

**Files:**
- Create: `datachallenge/shadow.py`, `datachallenge/checks_rows.py`
- Test: `tests/test_shadow.py`, `tests/test_checks_rows.py`

**Interfaces:**
- Consumes: everything from Task 3; `Entry.primary_key`, `Entry.join_candidates`, `Entry.columns`.
- Produces:

```python
# shadow.py
def shadow(sql: str, schema: str, name: str, body: str) -> str | None
def dedup_body(schema: str, name: str) -> str
def one_per_key_body(schema: str, name: str, key: str) -> str

# checks_rows.py
def rerun_value(ctx: VerifyContext, sql: str) -> float | None     # the located cell of a rewritten statement
def check_duplicates(ctx: VerifyContext) -> list[Finding]
def check_fanout(ctx: VerifyContext) -> list[Finding]
```

**Shadowing.** `shadow` returns the statement with a common table expression named `name` whose body is `body`, placed first, and every reference written as `schema.name` (either part optionally in double quotes, any case) replaced by the bare `name`. A bare `name` in the original then also resolves to the expression. If the statement already starts with `WITH`, the new expression is inserted directly after that keyword and followed by a comma. It returns `None` when the statement starts with `WITH RECURSIVE` or already defines an expression called `name`.

- `dedup_body` is `SELECT DISTINCT * FROM schema.name`.
- `one_per_key_body` is `SELECT * FROM (SELECT t.*, row_number() OVER (PARTITION BY key ORDER BY key) AS rn__ FROM schema.name t) k WHERE rn__ = 1`.

**Both checks** do nothing unless `ctx.located` is set. If `located.single_row` is false they return one `info` finding: "This check applies only when the answer is a single row." `rerun_value` runs the rewritten statement and returns the cell in `located.column` of its first row as a float, or `None` when the result is not exactly one row.

**Duplicates.** For each relation the located statement reads (`tables_read`) that has a catalogue entry and no declared primary key: count the rows and the distinct rows. Equal: nothing. Different: rewrite the statement with `dedup_body` and re-run. The number moves beyond the reproduce tolerance: `fail`, "{dataset} has {n} rows that exactly repeat another row. With them removed the answer is {new} instead of {reported}." It does not move: nothing. The statement cannot be shadowed: `info`, "{dataset} has {n} repeated rows; the query could not be re-run without them to see whether they affect the answer."

**Fan-out.** For each pair of in-scope relations the located statement reads, and each join candidate between them in the catalogue (declared or inferred), take each side in turn as the reduced side `R` with key `r`, and the other as `K`:
1. If `r` is unique in `R` (`count(*)` equals `count(DISTINCT r)` over non-null `r`), skip this side.
2. Rewrite the statement with `one_per_key_body(R, r)` and re-run.
3. The number does not move: nothing.
4. The number moves. Let `kept` be the columns of `K` of type `integer` or `number` that are not in its primary key, not a join column, and are mentioned in the statement. If `kept` is empty: nothing (the query is counting or totalling `R`, where more rows per key is meant). If every column in `kept` also exists by name in `R`: `warn`. Otherwise: `fail`.

Message for both severities: "Joining {K} to {R} on {r} repeats rows of {K}: {R} has up to {m} rows per {r}. With one {R} row per {r} the answer is {new} instead of {reported}. A total of {K}.{column} counted this way counts some rows more than once." For `warn`, append: "The column name also exists in {R}, so this may be intended."

At most one finding per pair of relations: the most severe.

### Task 5: Series break, missing values, catalogue caveats

**Files:**
- Create: `datachallenge/checks_series.py`
- Test: `tests/test_checks_series.py`

**Interfaces:**
- Consumes: everything from Task 3; `Entry.time_span`, `Entry.columns`, `Entry.caveats`, `Entry.units`.
- Produces:

```python
def monthly_levels(ctx: VerifyContext, entry: Entry, time_column: str, column: str) -> list[tuple[str, float, int]]
                                              # (month "YYYY-MM", level, non-null rows), in order
def find_break(levels: list[tuple[str, float]]) -> tuple[str, float] | None    # (first month after, ratio)
def check_series_break(ctx: VerifyContext) -> list[Finding]
def check_missing_values(ctx: VerifyContext) -> list[Finding]
def check_caveats(ctx: VerifyContext) -> list[Finding]
```

These three describe the data the answer rests on. They never produce `fail`.

A column is **used** when it belongs to a relation the located statement reads and `mentions(statement, column)` is true. A **measure** is a used column of type `number` or `integer` that is not in the primary key, not a candidate key and not a join column.

- `monthly_levels`: one query per measure, grouped by calendar month of the entry's `time_span` column. The level is the median on PostgreSQL (`percentile_cont(0.5) WITHIN GROUP`) and the mean elsewhere. Months with fewer than 20 non-null rows are dropped.
- `find_break`: needs at least 2 months on each side. Over every split point, take `ratio = median(levels after) / median(levels before)`. Choose the split whose ratio is furthest from 1 (by absolute logarithm). Return it only if the ratio is at least 5 or at most 0.2 **and** every level after lies on the far side, from every level before, of the geometric mean of the two medians. Levels of zero or below make the series ineligible.
- `check_series_break`: for each measure in an entry that has a time span: `warn`, "{dataset}.{column} changes level by about {ratio}x from {month}. That often means a change of unit or definition. If the query totals or averages across that date, check it treats both periods alike."

**In the loop.** When `cfg.checks` is not empty and an analyst finishes, `ask_analyst` calls `verify_analyst` (which opens its own read-only connection to the analyst's database, builds the context and runs the checks), then, if `cfg.second_opinion`, `second_opinion`. The text returned to the orchestrator is the analyst's final with one more key:

```json
"verification": {"verdict": "failed",
                 "findings": [{"check": "fanout", "severity": "fail", "message": "..."}]}
```

`info` findings from checks that could not run are included; evidence is left out. The whole text stays within the existing 4,000 character limit, cutting findings last. Each analyst's record in `Outcome.analysts` gains `findings` and `verdict`.

`Outcome.verdict` is the worst verdict among the analysts whose results stand: for each distinct set of datasets, only the most recent analyst call counts, so a successful retry clears an earlier failure.

When checks are configured, this paragraph is added to the end of the orchestrator's system prompt:

```
Each analyst result comes with a verification report. It is produced by code that re-ran the analyst's SQL and tested it against the data; it is not the analyst's opinion. If the verdict is "failed", do not pass the number on as it stands. Send the same datasets to an analyst once more with a task that states the finding and asks for a computation that avoids it, or, if that fails too, tell the user the answer could not be verified and why. If the verdict is "warnings", say in your answer which warnings bear on it.
```

**Second opinion.** `second_opinion` runs a fresh analyst, role `second_analyst`, with the same task and datasets. It is not shown the first answer. If both values are numbers and differ by more than 0.5% of the first: `fail`, check name `second_opinion`, "An independent analyst given the same task got {second} instead of {first}.", with the second analyst's SQL as evidence. They agree: nothing. The second analyst did not finish, or either value is not a number: `info`.

`replay` reads `runs.jsonl`, and for every analyst result that finished runs `verify_analyst` on its recorded `final` and datasets. No model is called. Each row holds: configuration, question id, repeat, analyst number, whether the question's final answer was right (from the recorded score), the verdict, the findings, the number of verification queries and the seconds taken.

Command: `python -m datachallenge verify-runs results/<timestamp> --catalogue ... --sources ... [--checks ...]` writes `verification.md` and `verification.jsonl` into that directory. Data may have changed since the run was recorded; the report says when the run was made.

The `run` command's `runs.jsonl` lines gain `verdict` and `findings`, and its `report.md` gains a section, **Verification**, shown when any configuration has checks.

`verification.md`, and the new section, contain:
1. **Caught and missed.** Over questions with a checked answer, a table of answer right or wrong against verdict `failed`, `warnings` or `passed`. Below it, in words: wrong answers the verifier failed (caught), wrong answers it passed or only warned on (missed), right answers it failed (false alarms).
2. **By check:** for each check, how many findings of each severity, and how many of its `fail` findings were on answers that were in fact wrong.
3. **Missed:** every wrong answer not failed: the question, expected and given values, the SQL, and the findings it did get.
4. **False alarms:** every right answer that was failed, with the finding.
5. **Cost:** mean verification queries and seconds per analyst result; for live runs, tokens spent on retries and on second opinions.
6. **Reading this:** the fixed text below.

```
A check that fails an answer is claiming the number is wrong. Judge it on two counts: how many wrong answers it caught, and how many right answers it failed. A verifier that fails everything catches everything.

"Missed" is the list to learn from. Each entry is a way of being wrong that no check here looks for.

Warnings describe the data, not the answer. A warning on a right answer is not a false alarm.
```

## Out of scope

Do not build these. They come after the owner has read the report.

- Student-facing material: the exercise in which students write checks themselves, a course module, a page on the site. The trap tables and `test_full_verdict_matches_the_trap_table` are the intended starting point for it.
- Planting traps in real data.
- A SQL parser, or checks that depend on one (for example detecting a filter the question implied and the query lacks).
- A check that the answer addresses the question asked. That needs a model's judgement and is a different kind of verifier.
- Checking the orchestrator's own arithmetic when it combines two analysts' results.
- Blocking answers. Findings annotate.
